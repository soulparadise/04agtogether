# Этап 4: испытания синхронизации

Дата: 29 октября 2026. Все изменения и испытания выполнены локально в `D:\AI Projects\o4agtogether`. Хостинг, домены, DNS, SSL, GitHub и Actions не изменялись; коммит, push и деплой не выполнялись.

## Реализовано

- `pnpm dev:lan`: frontend на конкретном частном IPv4 компьютера, backend только `127.0.0.1:3000`, API и Socket.IO через Vite proxy. Обычный `pnpm dev` сохраняет loopback-режим. Firewall и маршрутизатор не меняются.
- Dev-панель `?diagnostics=1`: позиции участников, абсолютное отклонение, RTT, коррекции, восстановление после соединения и с учётом разрыва. Сырые неодновременные позиции и оценка общей временной точки разделены. Никакие токены не отправляются в диагностике.
- Dev-профили задержки только для polling выбранной вкладки: `network=100`, `300`, `500`, `jitter`. Число задаёт миллисекунды на входящий HTTP-запрос **и** на исходящий ответ: номинальная прибавка к RTT вдвое больше. Jitter циклически меняет каждую сторону: 40/300/100/500/200/80 мс. Реальные RTT выше из-за очередей polling.
- Кнопка разрыва собственного соединения на 3 с. Защита Origin и полномочия владельца сохранены. Production не регистрирует диагностические события; UI диагностики и сетевые query-параметры отсутствуют в собранном frontend.
- Повторяемый сетевой benchmark с настоящими HTTP-запросами и отдельно обозначенными модельными часами видео. Исходные данные сохраняются в игнорируемом `test-results/`.

## Выявленные причины и исправления

1. При `waiting` периодическая коррекция продолжала перематывать зрителя в ещё не загруженные участки. Регрессионный тест подтвердил изменение позиции во время остановки буфера. Обычная коррекция теперь ждёт готовности; `canplay` выполняет актуальное догоняющее применение. Явная новая команда владельца по-прежнему принимается. Владелец не ставится на паузу из-за буфера зрителя.
2. Первый clock-запрос может попасть в очередь начальных polling-пакетов. На 500 мс/сторона наблюдались RTT около 2080 мс против последующих 1036 мс и плохая начальная оценка часов. Добавлены три ограниченных начальных пробы; полезное измерение времени применяется и от устаревшего ответа, но старые source/version никогда не заменяют актуальное состояние. Обычная периодичность и пороги коррекций сохранены.
3. В реальном браузере диагностические сообщения раз в секунду сами конкурировали с clock-запросами в polling-очереди: один замер отклонения на 500 мс/сторона составил **0,535 с**. Телеметрия теперь отправляется только после завершённых clock-проб и первоначальной калибровки. Повторная серия: **0,0684–0,0685 с**. Это наблюдение конкретного прогона, не гарантия для любой сети.
4. LAN HTTP не является secure context: генерация ID профиля через `crypto.randomUUID` там ненадёжна. Используется `crypto.getRandomValues`; это проверено тестом. Навигация сохраняет только разрешённые dev-параметры.

Нет новых управляющих событий от Viewer, циклических команд, БД, Redis или Docker. HTTP polling остаётся единственным транспортом Socket.IO.

## Результаты симуляции

**Это не замеры декодируемого видео.** Backend, Socket.IO polling и задерживающий HTTP relay настоящие; плееры заменены независимыми модельными часами с разными смещениями локального времени. Буферизация модели останавливает её часы, без сетевой загрузки MP4 и декодирования кадров.

Для каждого steady-профиля сохранены 12 стартовых замеров через 350 мс, затем ожидание трёх завершённых clock-проб и 20 steady-замеров через 350 мс. Стабилизация определяется по числу проб и времени, **не отбором низких отклонений**. Стартовые выбросы сохранены отдельно.

| Нет | 20 | 0,00088 | 0,00088 | 39 | 0 | 0,00088 |
| 100 мс | 20 | 0,16818 | 0,16818 | 228 | 0 | 0,16818 |
| 300 мс | 20 | 0,00441 | 0,00441 | 636 | 1 | 0,55653 |

Малое отклонение до обычного порога 0,45 с специально не вызывает постоянные seek. Коррекции здесь накоплены за сценарий, включая старт; не количество на каждый замер.

Модельное мгновенное догоняющее seek после готовности **не измеряет время декодирования HTML5**. Поле `joinConvergenceMs` в исходном JSON позднего входа включает обязательное ожидание 2500 мс: это время до контрольного замера, а не минимальное время достижения точности.

До исправления калибровки первоначальный прогон на 500 мс/сторона остановился с максимумом около 0,932 с; полных сырых данных того прогона нет. Дополнительная сохранённая серия до исправления дала максимум 0,49634 с (`test-results/calibration-before.json`). Прогоны показывают вариативность старта, поэтому результат нельзя обещать как постоянную точность.

## Фактические браузерные испытания

HTML5 MP4, разные вкладки с независимыми сессиями владельца и зрителя, один компьютер, приложение открыто через LAN-IP. Это отдельные реальные экземпляры HTMLVideoElement; физическое второе устройство не использовалось. Задерживающий middleware искусственно меняет polling, MP4 в steady-сериях загружается нормально.

Считывались реальные `video.currentTime`, paused/readyState и RTT панели. Последовательные замеры приведены к времени второго считывания по `Date.now`; это приближённое сравнение времён медиаплееров, **не анализ кадров или звука**. Сырые значения и отметки времени находятся в `test-results/browser-measurements.json`.

Один замер уже завершившегося видео исключён из steady-статистики и явно помечен в JSON; нулевая разница на конце видео не считается подтверждением синхронного воспроизведения.

Дополнительно проверено в браузере:

- **Настоящая остановка выдачи байтов MP4 только зрителю**: readyState=2, paused=false, позиция 1,967813 с и статус «Буферизация». После возобновления выдачи оба readyState=4, позиции 8,496835 / 8,493295 с. Последующий парный замер Δ=0,01455 с. Конкретное время от готовности буфера до восстановления не измерялось; модельное время вместо него не используется.
- **Разрыв соединения зрителя на 3 с**: статус потери связи, затем возврат того же участника без дубликата; панель зафиксировала 382 мс после подключения и 3400 мс с учётом разрыва. Последующий парный Δ=0,01498 с. Это один браузерный повтор плюс три независимых сетевых повтора выше.

- **Seek и Pause, 500 мс/сторона**: после доставки команд оба плеера остановились в позиции 29,136799 с, Δ=0. Время сходимости этого браузерного эпизода отдельно не измерялось. Пауза не включена в steady-таблицу.

## Повторение LAN-теста

```powershell
Set-Location 'D:\AI Projects\o4agtogether'
pnpm test:video
pnpm dev:lan
```

`test:video` требует установленного ffmpeg и создаёт собственный 90-секундный синтетический ролик. Для уже созданного файла повторять команду не нужно.

1. Откройте напечатанный адрес, например `http://192.168.88.240:5173/?diagnostics=1`, создайте комнату.
2. Откройте приглашение в независимой вкладке/на другом устройстве той же сети; для панели добавьте `?diagnostics=1`. Используйте другой никнейм и не дублируйте вкладку владельца вместе с sessionStorage.
3. Владелец задаёт **общий** URL `http://192.168.88.240:5173/test-media/sync-test.mp4`. В адресах другого устройства не использовать localhost/127.0.0.1. Если IP изменился, используйте новый из терминала.
4. Запустите видео, при необходимости нажмите «Начать просмотр» у зрителя. Сравнивайте активное воспроизведение после калибровки; не используйте конец ролика как steady-замер.
5. Меняйте профиль у зрителя ссылками панели. Проверьте Pause/Seek, поздний вход и кнопку разрыва. Профиль — добавленная задержка, фактический RTT читайте отдельно.

Для повторения **реального buffering** откройте комнату зрителя с `?diagnostics=1&mediaStall=1`. Владелец загружает общий URL MP4 с новым `?bufferRun=уникальный-id` и сразу запускает просмотр. Dev-middleware выдаёт зрителю первые 98 304 байта и задерживает оставшиеся до 10 с от первого запроса; новые Range-запросы того же run используют тот же срок. Владелец получает тот же URL обычным путём. Это работает только для фиксированного локального синтетического файла; произвольные URL сервер не загружает. Для нового опыта нужен новый bufferRun.

Проверка физического телефона пропущена по последнему указанию пользователя. Если позже понадобится: телефон в той же обычной Wi-Fi сети, открыть напечатанный LAN-IP и общее приглашение/MP4. Доступ с другого устройства может блокировать firewall или изоляция гостевой Wi-Fi сети; локальная проверка компьютера это не исключает. Системные настройки автоматически не меняются.

Остановить серверы: Ctrl+C. Перезапуск backend стирает комнаты из памяти; это существующее ограничение архитектуры. Восстановление после сетевого разрыва и восстановление после полного перезапуска процесса — разные сценарии.

## Ограничения и готовность

Цель Δ≤0,5 с после стабилизации достигнута во всех сохранённых steady-сериях модели и браузера. При старте, командах и разрывах отклонение временно больше; асимметрия реальной сети и очереди polling ограничивают оценку часов через половину RTT. Проверены искусственные задержки на одном компьютере, а не произвольный интернет-канал, мобильная ОС или радиоусловия Wi-Fi.

Нет непрерывного покадрового измерения, длительного soak-теста, испытаний фонового энергосбережения мобильных браузеров, DRM/HLS/MSE сторонних сайтов. Dev-метрики сообщаются клиентами и предназначены для диагностики, не для доверенного аудита. Dev-сервер доступен участникам выбранной локальной сети; не публикуйте его в интернет.

Механизм достаточно проверен для **следующего локального прототипа адаптера стороннего плеера / Chrome Extension**, с обязательной проверкой событий ready/waiting/playing, локального autoplay и управления каждым конкретным плеером. Готовность к production или всем киносайтам этими испытаниями не подтверждена. Разработка следующего этапа не начата.
