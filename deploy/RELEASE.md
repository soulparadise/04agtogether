## До первого изменения хостинга

Нужно отдельное разрешение пользователя на commit/push и запуск CI; затем на SSH-ключи/Secrets и первое переключение сайта. До этого ничего не загружать и не менять в панелях.

1. Через разрешённый SSH-доступ проверить именно каталог 04agtogether и фактический абсолютный путь Node **24.15+ ветки 24**. Он пока не подтверждён: не подставлять выдуманный путь. `pnpm prepare:beget` готовит шаблон; повторный запуск с проверенным путём (`pnpm prepare:beget /verified/path/to/node`) создаст `artifacts/hosting/deploy/site.htaccess.ready`. Этот пример пути требуется заменить реальным.
2. Подтвердить один процесс Node для этого приложения. Map комнат не разделяется между worker. Sticky sessions сохраняют маршрут одного клиента, но не общую память двух участников. [PassengerMaxInstancesPerApp](https://www.phusionpassenger.com/docs/references/config_reference/apache/) имеет глобальную область; не добавлять его. Per-site PassengerMaxInstances доступен только в Enterprise. Если Beget создаёт несколько workers, минимальное решение — согласовать с Beget ограничение **только 04agtogether** до одного процесса; без этого не включать автодеплой. Redis/VPS и глобальные изменения не предлагаются.
3. Проверить расположение site-level .htaccess и права записи только 04agtogether; при отказе остановиться, не делать общий chmod/chown. Заготовка использует родительский `.htaccess`, `public_html` остаётся document root, `app.js` — Passenger loader.

Проверка двух polling-клиентов и публичного случайного instance-маркера входит в release probe. Она выявляет наблюдаемую несовместимость workers, но успешный небольшой прогон не доказывает постоянный лимит Passenger. Сам лимит нужно подтвердить отдельно.

## Первое развёртывание после разрешения

1. После проверки секретов исходников создать согласованный commit и выполнить первый push. CI соберёт и проверит архив, production-расширение и shell-синтаксис. **BEGET_READY пока не создавать/не включать**: deploy-job пропускается.
2. На Beget подготовить внутри 04agtogether каталоги `incoming`, `releases`, `deploy`, `tmp`; загрузить только содержимое `artifacts/hosting` (маркер и deploy-файлы). Не заменять пока корневые `.htaccess`, `app.js` и public_html. Проверенная конфигурация должна называться `deploy/site.htaccess.ready`.
3. Отдельный ключ деплоя: одна согласованная запись в `~/.ssh/authorized_keys`, `restrict,command="bash /home/s/soulpab9/04agtogether/deploy/receiver.sh"`. Не заменять файл целиком и не трогать другие ключи. Этот шаг находится вне каталога сайта и требует явного согласования доступа аккаунта. Forced command допускает только upload/activate/restore-static, не eval произвольной команды.
4. Secrets окружения GitHub `production`: `BEGET_SSH_HOST`, `BEGET_SSH_KEY`, `BEGET_SSH_KNOWN_HOSTS`. Variables: `BEGET_IP=45.130.41.94`, при необходимости `BEGET_SSH_PORT`. Ключ хоста SSH сверить с надёжным источником, не доверять одному ssh-keyscan. Приватный ключ никогда не попадёт в Git, архив приложения или логи.
5. Первый запуск выполняется отдельно: с проверенным SHA-архивом CI и защищёнными переменными `node scripts/remote.mjs first`. Нужен GITHUB_SHA согласованного commit, не SHA старого состояния с незакоммиченными изменениями. Автодеплой не используется для первоначальной настройки.

`first-release.sh` сначала проверяет аккаунт, точный корень, конфигурацию, Node, checksum и пути архива. Затем `backup-static.sh` создаёт **полный снимок public_html и прежних корневых .htaccess/app.js**, извлекает его в проверочный каталог и сравнивает данные. Лишь после успешной проверки активируется приложение. Старый public_html перемещается в приватную резервную копию, не удаляется; ACME-файлы сохраняются.

Проверяются HTTPS/release SHA, SPA, два HTTP polling-клиента (web + Origin расширения), общая комната, Play/Pause/Seek и права. Поток видео сервер не загружает. Сбой первого запуска вызывает возврат к статическому снимку. Позднейшие deploy/rollback используют прежний current/previous и возвращают прошлую версию при сбое. Общих перезапусков нет: только `04agtogether/tmp/restart.txt`.

6. После первого успеха проверить браузером: главная HTTPS, два участника из интернета, production-расширение и реальные Play/Pause/Seek. Read-only проверкой убедиться, что kashalotik.ru продолжает отвечать. Не изменять его файлы/конфигурацию. Только после этих проверок отдельно включить `BEGET_READY=true` для будущего автодеплоя main.

## Откат

- К предыдущему приложению: workflow **Restore an existing Beget release**, поле release — полный SHA сохранённого релиза.
- К исходной статической странице: тот же workflow, поле release — **static**; либо через согласованный SSH-ключ команда **restore-static**, либо `bash /home/s/soulpab9/04agtogether/deploy/restore-static.sh` с административного доступа.
- `restore-static.sh` сверяет checksum, извлекает проверенный снимок, перемещает текущие файлы в `backups/.../displaced` и возвращает прежние public_html/конфигурацию. Рекурсивного удаления нет. Текущие ACME-файлы сохраняются. Затем отключить BEGET_READY перед дальнейшей работой.
- Серверный backup/restore пока проверен синтаксически и просмотром кода, не исполнен на хостинге. Реальная репетиция извлечения и сравнения встроена в первый запуск **до замены сайта**.

Комнаты по-прежнему в памяти: приложение автоматически запускается Passenger, но после перезапуска Node комнаты нужно создать заново. Постоянное хранение в этот релиз не добавлялось.
