## Локальная разработка из исходников

Требуются Node.js 24.15+ (ветка 24) и pnpm 11.25.0. Все команды выполняются в корне проекта:

```powershell
Set-Location 'D:\AI Projects\o4agtogether'
pnpm dev
```

Если зависимости ещё не установлены, предварительно выполнить `pnpm install --frozen-lockfile`. Для обычного запуска не нужны ни сборка, ни каталог `release/`, ни настройки Beget.

Открыть **http://127.0.0.1:5173**. Backend слушает только **127.0.0.1:3000**. Vite перенаправляет `/api` и `/socket.io` на backend, сохраняя Host и Origin. Production-проверка Origin не отключается. Проверка API через Vite: http://127.0.0.1:5173/api/health.

`pnpm dev` запускает оба сервера в одном процессе под Node watch. Изменения backend перезапускают процесс целиком; frontend обновляется через Vite. Ctrl+C останавливает оба сервера. При занятом порте запуск завершается ошибкой, а не переключается незаметно на другой порт.

Для независимого перезапуска backend можно работать в двух терминалах:

```sh
# Терминал 1
pnpm dev:backend
# Терминал 2
pnpm dev:frontend
```

Socket.IO использует только HTTP polling, без WebSocket upgrade. Собственный WebSocket Vite используется для обновления интерфейса при разработке и не меняет транспорт приложения. При временной потере соединения клиент восстанавливает участие в комнате. Полный перезапуск backend, в том числе Node watch, удаляет комнаты из памяти; интерфейс объясняет, что нужно создать новую комнату.

## Локальная сеть и испытания синхронизации — этап 4

```powershell
pnpm test:video # один раз: нужен установленный ffmpeg
pnpm dev:lan
```

Терминал печатает адрес приложения и общий адрес MP4. На проверенном компьютере это **http://192.168.88.240:5173** и **http://192.168.88.240:5173/test-media/sync-test.mp4**. Адрес может измениться. Владелец и телефон должны открывать приложение и видео через напечатанный LAN-IP, а не `127.0.0.1`. Backend остаётся на `127.0.0.1:3000`; Vite сохраняет proxy и проверку Origin, Socket.IO остаётся на HTTP polling.

LAN-режим слушает конкретный частный IPv4 интерфейса; `0.0.0.0` и публичный IP не используются. При нескольких интерфейсах можно указать фактический адрес нужного:

```powershell
$env:DEV_LAN_HOST = '192.168.88.240'
pnpm dev:lan
# После остановки, для возврата к автоматическому выбору:
Remove-Item Env:DEV_LAN_HOST
```

Программа не меняет firewall, маршрутизатор или проброс портов. Проверка с физического смартфона пока не выполнена; локальный запрос к LAN-IP не доказывает доступ с другого устройства.

Добавьте `?diagnostics=1` к адресу комнаты в обеих вкладках. Панель показывает позиции, RTT, коррекции и время восстановления. Удалённые позиции приходят неодновременно: сырое отклонение и приведённая ко времени оценка подписаны отдельно. Токены в диагностику не передаются. Панель и обработчик диагностических событий доступны только в разработке.

Ссылки в панели включают задержку `100`, `300`, `500` мс **на каждую сторону HTTP-запроса**, либо переменную задержку `40–500` мс. Это означает примерно +200/+600/+1000 мс к RTT до очередей polling. Задерживается только Socket.IO выбранной вкладки. Кнопка разрыва отключает её соединение на 3 секунды.

```powershell
pnpm test
pnpm test:network
pnpm build
pnpm smoke
```

`test:network` использует настоящий HTTP polling с задержкой, но модельные часы плееров: его результаты **не являются замерами HTML5-видео**. Он сохраняет исходные измерения в игнорируемый `test-results/network-simulation.json`. Браузерные измерения выполнены отдельно. Установившееся отклонение во всех проверенных профилях было меньше 0,5 с; при старте на высокой задержке наблюдались большие переходные отклонения.

## Комнаты и участники — локальный MVP

На главной введите никнейм (1–32 символа) и нажмите «Создать комнату». Приглашение имеет вид `/room/{roomId}`: идентификатор содержит 128 случайных бит, токенов в URL нет. Друг открывает ссылку в отдельной вкладке, вводит свой никнейм и входит зрителем. Владелец обозначен отдельно, может менять название комнаты (1–80 символов), источник видео и общее воспроизведение.

Для ручной проверки откройте два независимых окна/вкладки без дублирования вкладки владельца. В первой создайте комнату, во второй откройте приглашение и войдите под другим никнеймом. Проверьте список, смену названия владельцем, обновление его страницы и выход зрителя. Обычный `pnpm dev` доступен только на этом компьютере. Для других устройств той же сети используйте отдельный LAN-режим ниже. Действующий soulparadise.ru по-прежнему показывает тестовую страницу.

Каждый участник получает секретный 256-битный `sessionToken`. У владельца дополнительно есть отдельный 256-битный `ownerToken`. Секреты хранятся в `sessionStorage` своей вкладки, переживают обновление страницы, не входят в приглашения и снимки комнаты и не выводятся сервером в логи. Сервер хранит хеши токенов в модели комнат, а роль определяет по своей записи владельца, а не по никнейму или переданному клиентом полю роли. Токены являются доступом к сессии: их нельзя передавать другим людям. Если хранилище браузера недоступно, интерфейс предупреждает о потере сессии после обновления.

Копирование/дублирование вкладки может скопировать её sessionStorage средствами браузера. Восстановление с действительными токенами заменяет прежнее подключение той же сессии без дубликата участника: браузер иногда оставляет старый polling активным после обновления страницы. Предыдущее подключение сразу теряет членство и получает `room:session-replaced`; старая вкладка очищает свои токены, показывает сообщение и может войти отдельным зрителем. Одновременно одна сессия управляет только одним подключением. Повторные create/join на том же активном подключении не дублируют комнату/участника. Закрытие вкладки или очистка её хранилища может удалить токены: восстановления владения через аккаунт в MVP нет. Обновление той же вкладки поддерживается.

Временно отключившийся участник отображается офлайн. Зритель может восстановить ту же идентичность в течение 2 минут; позже его запись удаляется. Явный выход зрителя удаляет запись сразу. Запись владельца сохраняется до удаления комнаты, в том числе при явном выходе; в той же вкладке он может вернуться по сохранённому приглашению. Права никому не передаются. Комната удаляется после 30 минут без подключённых участников; очистка выполняется каждые 30 секунд и перед обработкой событий. Пока хотя бы один участник подключён, комната сохраняется.

Ограничения процесса: до 200 комнат, до 20 участников на комнату (включая временно отключённых). Хранилище — обычный Map в одном процессе Node.js. Это соответствует текущему локальному dev-запуску: один backend и один Vite. Несколько backend-процессов/Passenger workers пока не поддерживаются; sticky sessions сами по себе не синхронизируют комнаты. На хостинг этот MVP не установлен.

### Протокол Socket.IO

Запросы требуют acknowledgement. Успех возвращает `{ ok: true, ... }`, отказ — `{ ok: false, error: { code, message } }`.

| Событие | Поля запроса | Результат |
|---|---|---|
| `room:create` | `nickname` | Снимок комнаты, ID участника, его sessionToken и ownerToken |
| `room:join` | `roomId`, `nickname` | Снимок комнаты, ID зрителя и его sessionToken |
| `room:resume` | `roomId`, `participantId`, `sessionToken`, для владельца также `ownerToken` | Восстановление того же участника без дубликата |
| `room:leave` | `{}` | Выход из текущей комнаты |
| `room:update` | `title`, `ownerToken` | Изменение названия только владельцем текущей комнаты |
| `room:state` | Сервер → клиенты | Публичный снимок: id, title, revision, ownerId, participants |
| `room:session-replaced` | Сервер → прежнее подключение | Сессия восстановлена на другом подключении; прежнее членство отозвано |

В participants входят только id, nickname, role, connected. Версия revision увеличивается при изменениях. Снимок комнаты также содержит актуальный playback, описанный ниже. Play/Pause/Seek используют ту же комнату и проверяют владельца на каждом защищённом событии.

Автотесты `test/rooms.test.cjs` проверяют создание, обновления участников, разные комнаты, права, подделку владельца, приватность снимков, обновление/переподключение, тайм-ауты, повторные запросы и ограничения. `pnpm test` включает эти тесты и проверки предыдущего этапа.

## Синхронный HTML5-плеер — этап 3

Владелец вставляет прямую HTTP(S)-ссылку на MP4, WebM или другой нативно поддерживаемый браузером видеофайл. Он управляет общими Play/Pause и перемоткой кнопкой и полосой позиции. Зритель не отправляет управляющих команд. Громкость, mute и полноэкранный режим индивидуальны для каждого плеера и в протокол не входят.

### Модель и синхронизация

`backend/playback.cjs` хранит source (type/url), случайный sourceId, status, basePosition в секундах, updatedAt по монотонным часам, duration и version. Время на сервере измеряется через `performance.now()`, независимо от системных часов. Snapshot добавляет serverNow и вычисленную position. При Play позиция равна basePosition плюс прошедшее время; при Pause она неизменна. Известная длительность ограничивает позицию и определяет окончание. Play в конце начинает видео заново. Смена источника создаёт новый sourceId, увеличивает version и сбрасывает позицию, длительность и статус на паузу.

`HTML5VideoAdapter.mjs` предоставляет load, play, pause, seek, getCurrentTime, getDuration, getPlaybackState, destroy и события готовности/буферизации/ошибки. Смена источника останавливает старый ресурс и сбрасывает src через load(); destroy снимает обработчики и освобождает ресурс.

`PlaybackSync.mjs` использует только интерфейс адаптера. Снимки старой версии и старого источника не перезаписывают новые. Клиент получает полное состояние каждые 2 секунды, измеряет RTT и оценивает смещение монотонных часов по середине запроса/ответа; выбирается минимальный RTT из последних 8 измерений. По этому смещению вычисляется текущая серверная позиция. Это приближение предполагает достаточно симметричную задержку сети.

При обычном воспроизведении коррекция выполняется при отклонении больше 0,45 с и не чаще раза в 1,5 с. При новой команде или готовности после буферизации применяется актуальная позиция с допуском 0,08 с. Мелкие отклонения не вызывают перемотку. Постоянной коррекции скорости нет. timeupdate не отправляется в Socket.IO. Управляющие команды идут только от действий владельца; локальные события play/pause/ended не транслируются обратно. Единственное автоматическое изменение — однократное сообщение владельца с длительностью после чтения метаданных.

### События воспроизведения

| Событие | Доступ и поля запроса | Ответ / эффект |
|---|---|---|
| `playback:source` | Owner: ownerToken, expectedVersion, url | Новый источник и sourceId, пауза, позиция 0 |
| `playback:play` | Owner: ownerToken, expectedVersion, sourceId | Начало/продолжение общего воспроизведения |
| `playback:pause` | Owner: те же поля | Фиксация актуальной позиции |
| `playback:seek` | Owner: те же поля + position | Общая перемотка с сохранением режима |
| `playback:metadata` | Owner: те же поля + duration | Известная длительность, ограничение позиции |
| `playback:get` | Любой текущий участник: `{}` | `{ ok: true, roomId, state }` с полной актуальной позицией |
| `playback:state` | Сервер → только участники этой комнаты | `{ roomId, state }` после изменения |

На каждую управляющую команду сервер проверяет текущее членство, собственную запись владельца, ownerToken и expectedVersion. Для действий над существующим видео дополнительно проверяется sourceId. Успех подтверждается acknowledgement с state. Ошибка возвращает `{ ok: false, error: { code, message } }`; при устаревшем состоянии также возвращается актуальный state. Очередь команд клиента сериализует действия владельца. Запросы повторного управления со старой версией не применяются.

URL допускает только http/https, без встроенного логина/пароля и управляющих символов, длиной до 4096 символов. Backend не загружает URL и не проксирует видео: каждый браузер обращается к источнику напрямую. Расширение файла не используется как доказательство совместимости; формат, доступность и запреты внешнего сервера проверяются самим медиаплеером. Страницы киносайтов и DRM на этом этапе не поддерживаются. Числовые времена должны быть конечными, неотрицательными и не больше 7 дней; live-потоки с бесконечной длительностью не входят в этот MVP.

### Буферизация и автозапуск

Остановка буфера или ошибка у зрителя не ставит комнату на паузу. После готовности плеер догоняет серверную позицию. Если браузер отклоняет play() с NotAllowedError, показывается «Начать просмотр». Нажатие вызывает play() в пользовательском жесте и обновляет позицию; отказ не отправляет общую Pause. Ограничения автозапуска не обходятся.

### Воспроизводимый локальный тест

Для генерации собственного синтетического образца нужен установленный ffmpeg в PATH (для запуска приложения он не требуется):

```powershell
pnpm test:video
pnpm dev
```

Получится 90-секундный MP4 с тестовым изображением и тихим синусоидальным звуком, около 2,3 МБ. Он сохраняется в `frontend/public/test-media/sync-test.mp4`, исключён из Git. Вставьте владельцем ссылку `http://127.0.0.1:5173/test-media/sync-test.mp4`. Это статический локальный файл Vite, не видеопрокси. Если файл существует при локальной production-сборке, Vite скопирует его как public asset в release; публикация таких тестовых файлов на хостинг в этом этапе не выполняется.

Проверка: первая сессия на 127.0.0.1 создаёт комнату, вторая на localhost открывает тот же путь комнаты и входит зрителем. Проверить Play, Pause, полосу перемотки, обновление зрителя во время просмотра, кнопку «Начать просмотр» при отказе автозапуска и независимый mute. После смены URL позиция должна стать 0 у обоих. Несуществующий медиафайл должен дать понятную ошибку; после корректной новой ссылки ошибка очищается.

Автоматические тесты `test/playback.test.cjs` используют внедрённые монотонные часы и два/несколько настоящих Socket.IO polling-клиентов. `test/player.test.mjs` проверяет адаптер и синхронизацию на модели media element: устаревшие снимки, RTT, отсутствие обратной пересылки, отказ play(), буферизацию и очистку. Модель не заменяет реальную браузерную проверку.

Цель 0,5 с относится к нормальной сети после стабилизации, не является гарантией для фоновых вкладок, долгой буферизации, асимметричного интернета и разных устройств. Сервер хранит только состояние, не видео. Комнаты и воспроизведение по-прежнему теряются после полного перезапуска backend; несколько backend workers пока не поддерживаются.

Ручная проверка 29 октября 2026: два независимых origin (127.0.0.1 и localhost) во внутреннем Chromium-браузере на одном ПК. MP4 действительно воспроизводился у обоих. Проверены Play/Pause, перемотка до одинаковых 32,4 с, восстановление позиции после обновления зрителя, индивидуальный mute и недоступный источник с последующим восстановлением. После обновления браузер реально отказал в автозапуске со звуком: кнопка «Начать просмотр» позволила догнать продолжающийся общий сеанс без глобальной Pause. При естественном окончании оба video имели paused=true, ended=true, currentTime=90 и статус «Видео завершено». Проверены мобильные controls обеих ролей на ширине 390 px без горизонтального переполнения.

В трёх выборках во время воспроизведения (примерно на 14-й, 62-й и 71-й секундах) сравнивались DOM-свойства video.currentTime двух плееров с поправкой на разницу моментов чтения Date.now() (0–1 мс). Получены отклонения около 0,009 / 0,020 / 0,005 с. Это измерение текущих времён медиаплееров на loopback, не покадровое измерение изображения и не результат испытания через интернет между разными устройствами.

## Проверки и production-сборка

```sh
pnpm test
pnpm test:dev
pnpm build
pnpm smoke
pnpm start
```

`test:dev` проверяет исходный backend через настоящий Vite proxy: API, два polling-клиента, отклонение постороннего Origin и переподключение после перезапуска backend. Тест использует свободные loopback-порты и останавливает свои серверы.

`build` пересоздаёт `release/`. `smoke` проверяет уже собранное приложение. `start` запускает **production-сборку**, поэтому для него нужен результат `build`. При проверке production остановить dev backend: по умолчанию оба используют порт 3000.

Production-сайт локально: http://localhost:3000. Backend обслуживает frontend, `/api` и `/socket.io` на одном origin. Сборка backend включает JS-зависимости, поэтому на хостинге не требуется npm install.

## Первый публичный релиз — этап 8

Приложение опубликовано на **https://soulparadise.ru**: Beget, HTTPS и HTTP polling. IP deployment receiver — **45.130.41.94**. Постоянный лимит Passenger ещё требует подтверждения; автодеплой выключен.

Этап 10: сервер хранит версионированный выбор плеера/озвучки. Только Owner меняет его; позиция и Play/Pause при переключении сохраняются, старые команды источника отклоняются. Расширение узнаёт Allplay по наблюдавшемуся video.allplay__video, player-venom — по его модулю. На исследованной странице Lordfilm поддержаны реальные вкладки Full HD / Плеер 2 и верхние меню озвучек обоих плееров. Совпадение определяется по названию/ID, не по номеру; внутренние аудиодорожки Allplay отдельно не поддерживаются. Автоматическое действие допускается только при однозначных DOM-признаках; иначе popup сообщает точные названия и предлагает ручной выбор с явным подтверждением. Для нераспознанного переключателя владелец указывает точное название в popup. Это не универсальная поддержка киносайтов.

Версия 0.2.5 исправляет последовательные переключения плеера/озвучки, обработку BDRip и пустой Extension-комнаты. Добавлен исследованный Плеер 3 (Playerjs, отдельное разрешение iframe; озвучка неизвестна). Скрытые и удалённые фреймы исключаются, результат асинхронного поиска сверяется с выбранной вкладкой. Неизвестная озвучка не подменяется старой. Уведомление размещено слева по центру video и не закрывает нижнюю панель. Подробности и ограничения фактической проверки: `extension/SITE-SUPPORT.md`.

Версия 0.2.6 устраняет воспроизведённую гонку между bind/start новой рамки и ожидание metadata до запуска ленивого Allplay. Повторное подтверждение проверяет реальный источник и восстанавливает подключение, не заменяя обнаруженную озвучку ожидаемой. Техническая остановка прежнего video не отправляет общую Pause. Автозапуск по-прежнему ограничивает браузер; при отказе требуется «Начать просмотр». Двухпользовательский прогон установленной версии на реальном сайте необходимо подтвердить вручную.

Версия 0.2.7 добавляет необязательный вход по имени и паролю в существующие комнаты. На главной доступны создание и вход; приглашение по ссылке по-прежнему не требует пароля. Owner настраивает отдельное имя входа в блоке приглашения: NFKC, схлопывание пробелов, без учёта регистра, уникальность среди живых комнат. Пароль 8–128 символов не возвращается клиентам, хранится только scrypt-v1 с индивидуальной солью в прежнем приватном атомарном checkpoint. Вход выдаёт обычную сессию Viewer, которую существующий polling-сокет продолжает через room:resume. Пароли идут POST JSON на `/api/rooms/join` и `/api/rooms/access`, не в Socket.IO или URL. В production требуется HTTPS; локальная проверка допускается только на loopback development-сервере. Лимит: 10 попыток на сетевой адрес за 5 минут и максимум две параллельные проверки на процесс. Адрес берётся из соединения, без доверия произвольному X-Forwarded-For; если хостинг скрывает клиентов за общим прокси, лимит может быть общим. Каталога комнат нет. Пустые комнаты удаляются через прежние 30 минут, имя освобождается.

Создание комнаты на сайте теперь переходит на её URL полной загрузкой документа, чтобы Chrome external messages имели контекст `/room/<id>`, а не первоначальной главной страницы при pushState. Строгая проверка чужих комнат сохранена. Расширение повторно проверяет текущую вкладку сайта перед открытием фильма, не использует привязку к другому фильму/комнате и продолжает существующую Owner-сессию вместо создания второй комнаты. Настройки входа и повторный выбор страницы доступны также Owner, чей просмотр уже управляется расширением; пароль передаётся его приватным worker через HTTPS API. Полный запуск в установленном Chrome требует ручного подтверждения.

Версия 0.2.8 учитывает HTTPS при работе за Passenger: только в его runtime используются защищённые заголовки `!~Passenger-Proto` и `!~Passenger-Client-Address`. В обычном Node клиент не может включить доверие к ним; произвольный X-Forwarded-Proto не разрешает передачу пароля. [Документация Passenger](https://www.phusionpassenger.com/docs/advanced_guides/in_depth/node/secure_http_headers.html). Настройки SSL и прокси хостинга не изменяются.

Production loader включает приватные атомарные checkpoints комнат вне public_html. Сохраняются хеши credentials, не открытые токены; после перезапуска восстанавливаются реальные ID, роли, выбор источника и позиция с учётом прошедшего времени. Рабочий snapshot совместно не записывается несколькими Node-процессами: дополнительный writer отказывается запускаться. Повреждённый checkpoint не подменяется пустыми комнатами. При аварии строго во время захвата startup.lock потребуется его проверка администратором; постоянный лимит Passenger по-прежнему важен. Dev по умолчанию остаётся в памяти. Комнаты без участников истекают через 30 минут; старые комнаты до внедрения checkpoint восстановить нельзя.

Production-сборка приложения: `pnpm build`; проверка собранного релиза: `pnpm smoke`; архив: `pnpm package:release`. Preview `artifacts/local.tgz` не является SHA-релизом и не активируется на сервере. Тестовый MP4 в публичный build не попадает.

`pnpm build` также собирает production-расширение в `extension/dist-production`, создаёт ZIP и metadata в `release/frontend/downloads`. Версия берётся из manifest. Стабильная ссылка: **https://soulparadise.ru/downloads/04agtogether-extension.zip**; versioned ZIP доступен рядом. Сайт показывает скачивание и инструкцию на главной/странице приглашения и в режиме Extension. Для обновления заменить содержимое той же папки, перезагрузить карточку расширения и вкладки; удалять расширение не нужно. Идентичность сохранена. Dev-сборка `pnpm build:extension` остаётся отдельной.

Google Chrome — основной браузер. Для Edge/Opera/Brave/Vivaldi предусмотрены адреса и ручной выбор, но фактическая совместимость не заявляется без испытания. Настольная [инструкция Яндекса](https://yandex.ru/support/browser/ru/personalization/extension) описывает CRX3; здесь CRX3 и ключи подписи не создаются, ZIP-установка в Яндексе не подтверждена. Firefox, Safari и мобильные браузеры не объявляются поддерживаемыми.

[Порядок первого запуска, защищённые действия и откат](deploy/RELEASE.md). Скрипты сохраняют и проверяют исходную статическую страницу до замены и умеют восстановить её. GitHub deploy остаётся выключенным до отдельного включения BEGET_READY после успешного первого запуска. Secrets пока не настроены. Перед commit/push, ключами и заменой сайта требуется отдельное согласование пользователя.

Лимит одного процесса Passenger необходимо подтвердить только для 04agtogether: sticky sessions сами по себе не разделяют память комнат между workers. Глобальные настройки сервера не меняются. После перезапуска Node комнаты теряются, приложение остаётся способно запускаться заново.
