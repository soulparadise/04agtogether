## Локальная проверка

Node.js 24.15+ (ветка 24), pnpm 11.25.0:

```sh
pnpm install --frozen-lockfile
pnpm test
pnpm build
pnpm smoke
pnpm start
```

Сайт: `http://localhost:3000`. Проверка backend: `/api/health`. Socket.IO: `/socket.io/`, только polling, без upgrade. Клиент и backend используют один origin. Сборка backend включает JS-зависимости: на хостинге не требуется npm install. Необязательные нативные ускорители WebSocket не используются.

## Предполагаемая структура Beget

Всё размещается исключительно внутри отдельного сайта `04agtogether`:

```text
04agtogether/
  public_html/             # document root, .htaccess и ACME challenge files
  releases/<commit SHA>/
    frontend/              # результат Vite
    backend/app.js         # отдельная CommonJS-сборка Node.js
    backend/tmp/restart.txt
    release.json
  current -> releases/<SHA>
  previous -> releases/<previous SHA>
  incoming/                # архивы и их SHA-256
  .deployment-ready        # только после проверки фактического размещения
```

Passenger направляет запросы в корневой загрузчик `app.js`, который подключает `current/backend/app.js`; Node.js обслуживает frontend и API. `public_html` остаётся обычным каталогом для ACME. Не класть исходники, архивы, ключи или `.env` в document root.

`deploy/site.htaccess.example` — шаблон для родительского каталога `04agtogether/.htaccess`, по размещению существующего ws-test. Настройки нового приложения ещё требуют проверки. Абсолютный корень сайта, путь к Node.js и допустимое расположение директив нужно сверить с панелью и существующим ws-test, читая его настройки без изменений. Если Beget требует конфигурацию в родительском каталоге сайта, адаптировать расположение и проверки скрипта перед включением деплоя. Не менять глобальную конфигурацию Passenger, Apache, Nginx или права аккаунта.

Для HTTP polling шаблон включает `PassengerStickySessions on`, доступный в Passenger 5.1.12. Это привязывает запросы каждого клиента к процессу; будущим комнатам между разными процессами потребуется общий адаптер/хранилище. `PassengerMaxInstancesPerApp` не используется: это глобальная настройка. Источники: [Passenger Apache reference](https://www.phusionpassenger.com/library/config/apache/reference/), [Socket.IO multiple nodes](https://socket.io/docs/v4/using-multiple-nodes/).

## Включение Actions после подготовки хостинга

1. Создать отдельный сайт и привязать только soulparadise.ru и, если нужен, www. Проверить правильный IP в панели. Сохранить полный экспорт зоны Axelname и снимки привязок/SSL перед изменениями.
2. Установить первоначальную версию и проверить ответ нового сайта через Host/`curl --resolve` до переключения DNS. Не направлять трафик на неподготовленный каталог. Первоначальную установку и настройки Passenger ещё предстоит выполнить.
3. Переключить только A для корня и маршрут www; убрать конфликтующие маршруты GitHub Pages. Сохранить NS и все сторонние записи. Публичный DNS-снимок не заменяет экспорт всей зоны из панели.
4. Выпустить и проверить сертификат. Затем включить HTTP → HTTPS и www → основной домен. Шаблон учитывает HTTPS и `X-Forwarded-Proto`; фактическое поведение прокси и отсутствие циклов нужно проверить на Beget. Не включать правила для www до выпуска сертификата на www. ACME challenge исключён из редиректов.
5. Только после HTTPS-проверки снять старую привязку Pages в tplnrg. Не удалять репозиторий и историю.
6. Подготовить SSH-доступ к аккаунту soulpab9 отдельным ключом. Секреты GitHub: `BEGET_SSH_HOST`, `BEGET_SSH_KEY` (приватный ключ), `BEGET_SSH_KNOWN_HOSTS` (проверенная запись ключа сервера). Не получать доверие к ключу простым сканированием непроверенного сервера. Variables: `BEGET_IP` из панели, `BEGET_SSH_PORT` при необходимости. Секреты можно задать для environment `production`.
7. После проверки структуры создать внутри сайта каталоги `incoming`, `releases` и файл `.deployment-ready` с единственной строкой `soulparadise/04agtogether`. Установить проверенную родительскую .htaccess с точной строкой `PassengerAppRoot "<абсолютный корень сайта>"`, загрузчик `deploy/app.js` в корень сайта и каталоги `deploy`, `tmp`. Установить `deploy/receiver.sh` и `deploy/activate.sh` в каталог `deploy`; отдельному SSH-ключу назначить forced command `receiver.sh` с запретом PTY, forwarding, X11. Убрать стартовую статическую страницу из public_html, сохранив её резервную копию внутри этого сайта. Убедиться, что она не перехватывает запросы вместо Passenger.
8. После успешной первоначальной установки задать repository variable `BEGET_READY=true`. До этого deploy-job намеренно пропускается; CI продолжает выполнять проверки. Выполнить первый Actions-деплой и проверить реальный ответ с новым SHA. Отдельно проверить сценарий отката. Сейчас эти серверные проверки не выполнены.

Workflow запускает тесты, собирает frontend и backend, проверяет собранное приложение двумя polling-клиентами, упаковывает проверенный результат. SSH требует точный known_hosts и не выводит ключи. Серверный скрипт проверяет пользователя, физический корень и маркер сайта, использует flock, активирует версию заменой символьной ссылки и касается только её restart.txt. Общие службы не перезапускаются.

После активации выполняется HTTPS health-check на **IP из панели** с правильным SNI и проверкой SHA. При сбое скрипт возвращает предыдущую версию и проверяет её ответ. Если предыдущей версии нет, автоматическое восстановление невозможно: первая установка должна быть проверена отдельно до переключения домена.

Для ручного отката запустить Actions → Restore an existing Beget release с полным SHA сохранённой версии. Откат переключает frontend и backend вместе. Повторная загрузка уже существующего SHA запрещена; для повторной активации использовать workflow отката. Автоматической очистки старых версий нет: сначала проверить квоту, затем отдельно согласовать удаление старых архивов и версий.

Ни DNS, ни SSL, ни файлы kashalotik.ru или ws-test эти файлы не изменяют. Установка на реальном хостинге, проверка квоты, привязок, ключей и выполнение workflow требуют доступа к соответствующим панелям.
